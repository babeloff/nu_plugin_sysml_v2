= Parser Inconsistency
:toc: left
:toclevels: 3

[NOTE]
====
*Largely resolved in `sysml-v2-parser` 0.50.0.*
The two entry points now agree on the verdict for every file measured.
One criterion remains unmet — see <<What is still open>> — and resolving the
divergence turned a set of previously-passing models into hard failures, recorded
separately in xref:03-verdict-parity-fallout.adoc[spec 03].
====

`sysml-v2-parser` exposes two entry points, and through 0.49.0 they disagreed
about what a valid SysML v2 file is.
Neither was a superset of the other: each accepted things the other rejected.

This spec records the measured divergence, why `lint` exposed it as a `--mode`
flag rather than picking one silently, and how 0.50.0 closed it.

Originally measured against 0.48.0, re-measured unchanged against 0.49.0, and
re-measured against 0.50.0 — see <<Status as of 0.50.0>>.

== The two entry points

[cols="1,2,2"]
|===
| | `parse` | `parse_for_editor`

| Underlying
| `parse_root`
| `parse_with_diagnostics`

| Returns
| `Result<RootNamespace, ParseError>` — one error
| `ParseResult { root, errors }` — a partial AST plus every error

| Intended for
| Deciding whether a document is valid
| IDE and LSP features on half-written source

| Reached by
| `lint` default, `lint --mode strict`, plugin `lint sysml`
| `lint --mode edit`, plugin `lint sysml --mode edit`
|===

== The divergence ran both ways

Both tables below describe 0.48.0 and 0.49.0 behaviour.

=== Recovery rejected valid SysML

Constructs the strict parser accepted and the recovery path did not implement.
These were read at the time as *false positives*: correct models reported as
broken.

[cols="2,1,1"]
|===
| Construct | `strict` | `edit`

| `allocate action step to image;` in a part-definition body
| accepts
| rejects

| `part p : A;` in an action-definition body
| accepts
| rejects

| `foreach cfg in items { … }` in an action body
| accepts
| rejects

| `snapshot t_done { }` in an action body
| accepts
| rejects

| A comment whose continuation line reads `Word: text`, inside a
  part-definition body
| accepts
| rejects
|===

The last row was xref:01-fix-comment-block.adoc[its own spec] — the recovery path
resumed scanning inside a comment body.

That reading of the other four rows turned out to be *wrong*, and 0.50.0 is what
disproved it: strict was not parsing those constructs, it was silently dropping
them.
See <<Status as of 0.50.0>>.

Two of those four went further still: `foreach` is not a SysML v2 keyword at all —
the loop keyword is `for` — and `snapshot` has no precedent inside an action body.
So the table above records two constructs this workspace's models should never have
used, listed here as though the parser were at fault.
Both are now corrected in the models; see
xref:03-verdict-parity-fallout.adoc#_the_real_defects_found[spec 03].

For calibration, these were handled identically by both: a one-line `package`,
`individual` with a body, `require constraint { … }` in a `requirement def` or
`requirement` usage body, `flow a.o to b.i;`, and `calc def` with a `return`
expression.

=== Strict silently accepted invalid SysML

The strict parser returned `Ok` for input it could not parse, dropping what it did
not understand instead of reporting it.
These were *false negatives*: real mistakes that passed.

[cols="2,1,1"]
|===
| Malformed input | `strict` | `edit`

| `attribute x : String` — missing semicolon
| *misses*
| catches

| `attribut def X { }` — misspelled keyword
| *misses*
| catches

| `attribute x String;` — missing colon
| *misses*
| catches

| `attribute x : String = "oops;` — unterminated string literal
| *misses*
| catches

| `frobnicate def Q { }` — unknown keyword
| *misses*
| catches

| A stray extra `}`
| catches
| catches

| A missing closing `}`
| catches
| catches
|===

Confirmed at the library level, not just through the CLI: for `parts def A { }`,
`parse` returned `Ok` with a `RootNamespace` of one element — the package — and
the malformed declaration simply absent.
Structural brace errors were the class strict did catch, because they break the
document's shape rather than one declaration's syntax.

Neither mode caught everything: `%%% garbage %%%` inside a part-definition body
was accepted by both.

The divergence is closed.
Across the 72-case matrix behind this spec and spec 01, *all 72 cases now produce
the same verdict from both entry points*, up from 42.

=== What 0.50.0 changed

Upstream's `parse_root` verdict-parity work (PR `#3`, tracked as
`PARSER_BACKLOG_ROADMAP.md` §6, an audit dated 2026-07-30) made the strict entry
point stop silently accepting what it could not parse.
That single change is what met criteria 2 and 3.

It also invalidated criterion 1's premise.
Upstream's own audit note is explicit that the §6 grammar gaps were "previously
masked by `parse_root` silently accepting them" — so `allocate`, `part` in an
action-definition body, `foreach` and `snapshot` were never being parsed by
strict.
Strict's `Ok` was the false negative from the second table, not evidence that the
grammar accepted them.
With the masking gone, all four are now rejected by *both* entry points, which is
consistent behaviour over an incomplete grammar rather than a disagreement.

The `require constraint { … }` case this spec previously flagged as an open
question resolves the same way: it is now rejected by both in a part-definition
body, and accepted by both in a `requirement def` or `requirement` usage body.

=== What is still open

Criterion 4: `%%% garbage %%%` in a part-definition body is still accepted by both
entry points.
`sysml-v2-cli/tests/lint.rs::both_modes_reject_malformed_declarations` records
that gap alongside the six inputs that are now caught.

Written up for upstream in <<Upstream bug report>>.

=== Arbitrary non-SysML text is accepted inside part bodies

*Summary.*
Both `parse` and `parse_for_editor` accept a part definition or part usage body
containing text that is not SysML at all, reporting no diagnostic and silently
producing an AST with the content absent.
Every other body kind rejects the same text.

*Reproduction.*

[source,sysml]
----
package Shop {
    part def Wheel {
        %%% this is not SysML at all %%%
    }
}
----

*Expected.* A syntax error, from both entry points.

*Actual.* `lint --mode strict` and `lint --mode edit` both report `ok`, exit 0.

*Scope.* The gap is confined to the two part body kinds:

[cols="2,1,1"]
|===
| Body containing `%%% this is not SysML at all %%%` | `parse` | `parse_for_editor`

| `part def A { … }`
| *accepts*
| *accepts*

| `part a : A { … }`
| *accepts*
| *accepts*

| `package P { … }`
| rejects
| rejects

| `action def A { … }`
| rejects
| rejects

| `attribute def A { … }`
| rejects
| rejects

| `port def A { … }`
| rejects
| rejects
|===

The `package` case rejects with `unexpected token in package body`, which is the
diagnostic the part cases should be producing too.

*Why it matters.*
This is the last surviving case of the class 0.50.0's verdict-parity work set out
to eliminate — input the parser cannot understand being dropped rather than
reported.
It is narrower than the pre-0.50.0 behaviour, since ordinary typos are now caught,
but the failure mode is the same: a clean parse is not proof the input was
understood.
Because `part def` and `part usage` bodies are where most of a structural model
lives, it is a consequential place for the gap to remain.

*Suggested fix.* Route the part definition and part usage body element dispatch
through the same unrecognized-token diagnostic the package body path already uses,
rather than letting an unmatched alternative fall through as success.

=== Consequence: the fallout

Making strict honest surfaced every grammar gap it had been hiding, across this
workspace's models as well as upstream's own validation corpus.
29 project-authored `.sysml` files that passed `lint` under 0.49.0 initially failed
it; 18 still do, the other 11 having turned out to be defects in the models rather
than parser gaps.

That is not a regression in this crate and not a defect in the models; it is
previously-hidden information becoming visible.
It is recorded, classified and quantified in
xref:03-verdict-parity-fallout.adoc[spec 03].

== Why `lint` exposed a flag rather than choosing

Kept for provenance; the reasoning below describes 0.48.0–0.49.0.

Both answers were useful, and neither was trustworthy alone.

`strict` was the default::
  It answered the question a validator is asked — does the grammar accept this
  file — and it did not reject correct models.
  Its blind spot was that a typo could pass, so a clean `lint` run was weaker
  evidence than it looked.

`edit` was available::
  It reported every problem in a file rather than the first, which is what makes
  diagnostics usable, and it caught the ordinary typos strict dropped.
  Its cost was false positives on valid constructs, which made it unusable as a
  gate.

Running both and reading the union was then the most thorough check available.

Under 0.50.0 that advice is obsolete: the verdict is the same either way, so
`--mode` is now a choice about *diagnostic verbosity* — one error or all of them —
which is the legitimate difference between the two entry points.

== Effect on this workspace's models

Historical, as measured under 0.48.0/0.49.0.

All sixteen models in the surrounding campaign repositories passed `strict`.
Five failed `edit`, entirely on the constructs in
<<Recovery rejected valid SysML>>:

[cols="2,1,1"]
|===
| Model | `strict` | `edit` errors

| `experiment-workflow.sysml` | ok | 7
| `carla-system-experiment.sysml` | ok | 10
| `benchmark-surrogate-experiment.sysml` | ok | 6
| `carla-system-campaign.sysml` | ok | 2
| `benchmark-surrogate-campaign.sysml` | ok | 2
| the other eleven | ok | 0
|===

This is why the divergence mattered in practice rather than in theory: before the
mode flag existed, `lint` used the recovery path, and the five models carrying the
campaign design could not be validated at all.
Their failures were read as model defects for some time; they were not.

Under 0.50.0 these same five files fail *both* modes with the same counts, because
the constructs they use are genuine grammar gaps — see
xref:03-verdict-parity-fallout.adoc[spec 03].

=== A set this table does not cover

The five `.sysml` files under
`campaign/00-meta-campaign/docs/explanation/sysml/` failed `strict` as well as
`edit` under 0.49.0, so they were outside the sixteen counted above.
They open with a top-level annotation application carrying `:>>` bindings:

[source,sysml]
----
@ActionFlowViewMeta {
    :>> direction = LayoutDirection::TB;
}
----

These files are inputs to a separate diagram generator rather than models this
crate is asked to validate.
0.50.0 improves one of them — `action-flow-viewpoint.sysml` now passes — via the
new `metadata_keyword_prefix` support; the other four still fail.

== Provenance

The divergence surfaced during the 0.29.0 → 0.48.0 parser upgrade.
Under 0.29.0 `lint` used the recovery path exclusively, so the false positives
were the visible behaviour and the false negatives were unknown.
Switching the verdict to `parse` made the models pass and exposed the opposite
failure mode.
Both directions were then measured deliberately, which produced the tables above.

0.50.0 closed it from the strict side, and in doing so showed that half of what
had been measured — the first table — was an artifact of the false negatives in
the second.
