= Verdict-Parity Fallout
:toc: left
:toclevels: 3

`sysml-v2-parser` 0.50.0 stopped the strict parser silently accepting input it
could not parse.
That was the fix the verdict-parity work asked for, and it
worked — but it also revealed every grammar gap the silence had been hiding.

18 project-authored `.sysml` files that passed `lint` under 0.49.0 now fail it.
This spec records which, why, and what is actually actionable, so the red gate is
a known quantity rather than a mystery.

Measured against `sysml-v2-parser` 0.50.0, comparing `lint --mode strict` verdicts
against a 0.49.0 build of the same crate.

== Status as of 0.53.0

The crate was bumped 0.50.0 → 0.53.0 on 2026-08-04.
Four of the gaps this spec reported are closed, one new gap appeared, and the
project-authored red set changed shape rather than shrinking.

Closed upstream, each verified by direct probe against 0.53.0, and *removed from this
spec* along with their write-ups — a fixed bug is not a finding:

* `part p : A;` and the other `ActionBodyItem` members in an `action def` body
  (issue #13, was Bug 1)
* `action def X { … }` nested in a part-definition body (issue #14, was Bug 2)
* `interface x : T;` as a part-definition body member (issue #16, was Bug 5)
* `exhibit state X parallel { … }` (issue #17, was Bug 9)

Also probed as accepted, though they were never separate reports here:
`part :>> name { … }` in a part usage body, `assert constraint { … }` and `variation`
in an action body, and `allocate … to …;` in a part-definition body.

<<Bug 16: typed loop variable in a `for` loop>> is still open.
Bugs 10, 11, 12, 14 and 15 were *not* re-measured — treat their status here as
unverified against 0.53.0 rather than unchanged.
The surviving bug numbers are left as they are, so anything already citing them still
resolves.

Also closed, the last of the verdict-parity criteria:
`package P { part def A { %%% garbage %%% } }` was accepted by both modes through
0.50.0 and is now rejected by both, as `unexpected token in part definition body`.

=== The new gap: bare feature value assignment in a usage body

0.52.0 routed `connection_def_body` and `interface_def_body` through the same
recovery-node path the rest of the parser uses, and wired `collect_errors` to walk
those bodies *at all* — previously neither was ever collected into
`parse_with_diagnostics`, at any nesting level.
Diagnostics that had been silently dropped therefore became visible for the first
time, which is the same unmasking that produced this spec, one layer further in.

What it surfaced here is the terse feature-value form:

[source,sysml]
----
part 'kafka-probe' : GranuleArtifact {
    packageName    = "kafka-probe";     // unrecognized declaration `packageName`
    packageVersion = "0.1.0";           //   in part usage body
}
----

This is corroborated 56 times in the OMG official pilot examples — `toolName =
"ModelCenter";`, `status = StatusKind::tbd;`, `technicalRisk = medium;` and so on —
so by the evidence standard this spec already applies, it is a parser gap and not a
defect in our models.
It is now the second entry in `both_modes_reject_uncovered_grammar`.

*Do not rewrite the granule models to `attribute :>> packageName = …`.*
Thirteen `resources.sysml` files use this form and all thirteen went red on the
bump; rewriting them would encode a parser limitation into the models, which is
what <<Do not "fix" the models — but do check the language first>> exists to
prevent.

[#literal-prefix]
=== New bug: identifiers beginning with `null`, `true` or `false` are mis-lexed

Not yet filed upstream — no issue in the tracker mentions it and 0.53.0 is the
latest release.

The three KerML *literal* keywords are matched with a bare `nom::tag`, without the
trailing word-boundary assertion the rest of the parser applies, so an identifier
that merely starts with one is split into the literal plus a trailing fragment:

[source,sysml]
----
package P {
    action c : Campaign {
        flow env to nullPoint.env;    // unexpected token in action body
        flow env to trueValue.env;    // same
        flow env to falseAlarm.env;   // same
        flow env to zeroPoint.env;    // fine
    }
}
----

Exactly three prefixes are affected, and the boundary check is demonstrably present
elsewhere in the same file:

[cols="2,3"]
|===
| Affected | Not affected

| `null`, `true`, `false` — `expr.rs:138`, `:139`, `:285` use
  `tag(&b"true"[..])` and friends directly.
| `not`, `and`, `or`, `xor`, `implies`, `all`, `as`, `istype`, `hastype`, `meta`,
  `new` — the operators in the *same file* go through `keyword_token`
  (`expr.rs:402`, `:466`), which does check the boundary.

|
| Every declaration keyword — `part`, `in`, `out`, `flow`, `item`, `connect`,
  `about`, `ref`, `state`, `action`, `attribute`, `if`, `then`, `else` — routed
  through `lex.rs::starts_with_keyword`, which requires the next byte to be
  whitespace or one of `{ : ; [`.
|===

Case matters: `NullPoint` parses, because the literals are lowercase.
`nullpoint` and `null_point` both fail.

The fix looks like a one-liner per site — route the three literal parsers through
the `keyword_token` helper the operators beside them already use.

The reported position is the recovery point rather than the offending token — in the
original file the error landed on a *blank* line two lines further down, which is
<<bug-15,Bug 15>> again.
That is what made this expensive to find: bisection was necessary because the
diagnostic pointed at whitespace.

Found because the benchmark-surrogate campaign model used `nullPoint` for the
experiment at which detections reach zero. Renamed to `zeroPoint`; no workaround is
needed beyond not starting an identifier with one of the three literals.

== This is not a regression in this crate

Nothing in `sysml-v2-cli` changed behaviour.
The models did not change either.
What changed is that `parse_root` now reports what it previously dropped, so
constructs that were never being parsed are now visible as errors.

Upstream's own audit note (`PARSER_BACKLOG_ROADMAP.md` §6) states it plainly: the
grammar gaps were "previously masked by `parse_root` silently accepting them".
A clean `lint` run under 0.49.0 was therefore weaker evidence than it looked —
which is exactly what the verdict-parity analysis predicted, now demonstrated at
scale.

We support a pragmatic subset used by function-based behavior examples.
____

So these are acknowledged incompleteness, not rejected-because-invalid.
`PARSER_BACKLOG_ROADMAP.md` §6 lists G1–G30 as closed, but none of these
particular constructs appear there — they are gaps beyond that audit's scope.

=== A message that means nothing

`expected unit name inside '[ ]'` accounts for 10 of the 56 diagnostics and is
*not* tied to any one construct.
It appears for `part` in an action body, a nested `action def` and `part :>>` —
three unrelated constructs, and more before the withdrawn reports were removed.

In every observed case the reported line contains no `[` at all, and the reported
position is the header of an enclosing construct rather than anything resembling a
unit expression.
It is a mis-selected alternative's error surfacing as the file's verdict, not a
description of the input.
That symptom is gone as of 0.53.0, along with the grammar gaps that triggered it —
see <<bug-15,Bug 15>>.

=== Do not "fix" the models — but do check the language first

Every construct in the table above is legal SysML v2, except the chained-succession
row, which is flagged there.
Rewriting a model to satisfy the parser would be the same mistake made once already,
when the recovery path's false positives "were read
as model defects for some time; they were not."

`sysml-v2-cli/tests/lint.rs::both_modes_reject_uncovered_grammar` pins five of these
gaps deliberately, so the release that closes them fails the suite and prompts this
spec to be revised.
Its companion, `accepts_the_valid_forms_of_constructs_we_once_misreported`, asserts
the correct spelling of all five withdrawn cases, so the corrected models cannot
regress and the withdrawals cannot quietly come back.

The converse trap is just as real, and this spec fell into it *five times* — every
time by treating "our model does this and the parser rejects it" as evidence the
parser was wrong.
Four are now fixed as model defects; the fifth is recorded but left alone:

[cols="2,3"]
|===
| Written | Should have been

| `test case def X { … }`
| `verification def X { … }` — there is no `test` keyword

| `part :>> readings = a, b;`
| `= (a, b);` — `=` takes one expression

| `foreach x in xs { … }`
| `for x in xs { … }` — there is no `foreach` keyword

| `allocate action step to profile;`
| `allocate step to profile;` — endpoints are feature references, not declarations

| `first a then b then c;`
| one `then` per statement, continued with `then c;`
|===

Between them these accounted for 28 of the 83 substantive diagnostics originally
recorded here — 27 removed by the fixes, and one (the chained succession) still
present.
Two were caught in review rather than by measurement, and three more by the audit
those reviews prompted — because *measurement confirms what the parser does, never
whether it is right to do it*.

So before filing a gap, establish that the construct is real, independently of this
workspace's models.
<<Evidence audit>> applies the following to every surviving report:

* Check whether the parser has the token at all.
  `grep -r '"test"' src/parser/` and `grep -rn foreach src/` both returned nothing —
  which settles those two on their own.
* Look for the construct, *in the same body kind*, in OMG-authored SysML v2: the
  domain and systems libraries under `tools/sysmlv2/discussion/stds/sysmlv2/`, the
  `SimpleVehicleModel` from the OMG PTC 2025 submission at
  `tools/sysmlv2/discussion/docs/example/ptc-25-04-31.sysml`, and the training and
  pilot examples under `tools/sysmlv2/modeler/reference-examples/`.
  Position matters: `allocate` appears 22 times in that corpus, but never once in a
  part *definition* body, and never with a kind keyword on its endpoints.
* Find a *control* the parser accepts that expresses the same intent.
  If one exists, suspect the model.
  `allocate step to profile;` is accepted in the very body where
  `allocate action step to profile;` is not.
* *Reduce to the smallest input that still fails*, rather than trimming the model
  around the construct.
  The `allocate` report survived because its reproduction was copied from a model and
  kept a stray `action` keyword; dropping one token at a time would have found that
  immediately.

A diagnostic that names a construct is not evidence the construct is real.

== The real defects found

Six genuine model defects surfaced.
All are fixed.
Together they took the fallout from 29 files to 18, and they are the concrete
argument for adopting 0.50.0 despite the red gate: the honest parser found real
bugs that four prior releases had hidden.

=== Model defect 1: `:` where `:>` was meant

`granule/surrogate/decepticon-surrogate/sysmlv2/transport.sysml` declared four
part definitions with a typing operator instead of a specialization operator:

[source,sysml]
----
part def CameraChannel : ZmqChannel {      // was
part def CameraChannel :> ZmqChannel {     // now
----

`:` is a `FeatureTyping` and is only legal on a *usage*; a `part def` specializes
with `:>`.
The previous form had no valid reading, so nothing was lost in correcting it —
and 0.50.0's diagnostic named the fix outright:

----
invalid typing operator in part definition specialization: use ':>' instead of ':'
----

All four occurrences were corrected and the file now lints clean in both modes.

=== Model defect 2: `test case def` is not SysML v2

Six `test_cases.sysml` files — `carla-system/{flyer,npc,perception,validator}` and
`surrogate/{perceptacum,simulacrum}-surrogate` — opened their case definitions with
a construct the language does not have:

[source,sysml]
----
test case def WheelIsRound {           // was — no `test` keyword exists
verification def WheelIsRound {        // now
----

The SysML v2 form is `verification def`, per `VerificationCaseDefinition` in the
BNF.
Upstream implements it as `verification_case_def` in `src/parser/case.rs`, keyed on
the `verification` keyword with `def` required.

Verified: the parser accepts `verification def`, `case def` and `use case def`, and
has no `test` token anywhere.
All six files now lint clean in both modes; `test case def` was the sole cause of
failure in every one of them.

This one was initially misfiled as an upstream gap, on the strength of the
diagnostic's wording alone:

----
unexpected keyword `test` in package body
----

Calling `test` a "keyword" made it look like a recognized-but-unimplemented
construct.
It is not: the parser has no `test` token at all, and this is its generic report for
an unrecognized leading identifier — the same wording it produces for
`distancePerVolume` in <<bug-14,Bug 14>>.
The phrasing was worth fixing upstream in its own right; filed as part of
https://github.com/elan8/sysml-v2-parser/issues/18[issue #18] and fixed in 0.53.0,
which now says ``unrecognized declaration `test` in package body``.

=== Model defect 3: bare comma list where a sequence constructor was meant

`campaign/surrogate/benchmark-surrogate/sysml/benchmark-surrogate-campaign.sysml`
and `campaign/teds-playground/sysml/carla-system-campaign.sysml` each bound a
plural feature with a bare comma list:

[source,sysml]
----
part :>> parameters = loadLevel, messageRate;      // was
part :>> parameters = (loadLevel, messageRate);    // now
----

The base declaration is `part parameters : Parameter[1..*];`, so a collection is
wanted — but `=` takes a single expression, and a sequence needs `( … )`.

This one is unambiguous: two lines below the defect, the *same file* already used
the correct idiom for a different feature —

[source,sysml]
----
attribute :>> values = (10, 50, 100);
----

— so the parenthesized form was known to the author and simply missed here.
The OMG standard libraries use the same form throughout.

Both occurrences corrected.
Each file still fails on a genuine `foreach` gap, so the failing-file count is
unchanged; the diagnostic count drops by two.

The bracket form `= [pressure, tension];` is also rejected.
That is very likely correct — `[ ]` is multiplicity in SysML v2, not a sequence
literal — but it was not checked against the BNF, so it is an observation only, not a
claim.

The diagnostic this produced was itself misleading. Filed as part of
https://github.com/elan8/sysml-v2-parser/issues/18[issue #18] and fixed in 0.53.0,
which now reports the comma's own position and names the fix.

[CAUTION]
====
Case bodies are not validated.
`verification def V { attribut x : String; }` — with a misspelled keyword inside —
is accepted, because upstream captures the body with `loose_use_case_body`.
The same holds for `case def` and `use case def`.
So these six files now *parse*, but their bodies are not being checked, and the
`subject` / `verify` / `attribute` members inside them are effectively unverified.
This is the same class of gap as
https://github.com/elan8/sysml-v2-parser/issues/12[issue #12] and is worth adding
to it.
====

=== Model defect 4: `foreach` is not SysML v2

The loop keyword is `for`.
`foreach` does not exist — `grep -rn foreach src/` over the parser returns nothing,
and it appears nowhere in any OMG corpus, while `for` appears in both the standard
libraries and the training examples.

[source,sysml]
----
foreach cfg in configurations { … }        // was
for cfg in configurations { … }            // now
----

19 occurrences across five files:
`campaign/00-meta-campaign/sysml/{example-campaign/campaign,meta/parameter-space}.sysml`,
`campaign/surrogate/benchmark-surrogate/sysml/benchmark-surrogate-campaign.sysml`,
`campaign/teds-playground/sysml/carla-system-campaign.sysml`, and
`tools/sysmlv2/discussion/docs/example/camp/camp-inst.sysml`.
All corrected; 8 diagnostics removed.

Upstream implements this as `for_loop` in `src/parser/action.rs`, wired into both
`ActionDefBodyElement` and `ActionUsageBodyElement`.
Verified: `for s in spokes { … }` and `for n in (1, 2, 3) { … }` are both accepted.

=== Model defect 5: a kind keyword on an `allocate` endpoint

`allocate`'s endpoints are `ConnectorEndMember` — references to features that already
exist — not declarations.
Our models prefixed the source with `action`:

[source,sysml]
----
allocate action step to profile;      // was
allocate step to profile;             // now
----

`step` is already declared as `action step : TruthStep;` earlier in the same body, so
the keyword was both redundant and ungrammatical.

34 occurrences across five files:
`campaign/00-meta-campaign/sysml/meta/{experiment-pkg,experiment-workflow}.sysml`,
`campaign/surrogate/benchmark-surrogate/sysml/benchmark-surrogate-experiment.sysml`,
`campaign/teds-playground/sysml/carla-system-experiment.sysml`, and
`tools/sysmlv2/discussion/docs/example/exp/exp-exec.sysml`.
All corrected; 11 diagnostics removed.

*This was the clearest false gap of the five*, because the body kind was a red
herring.
The withdrawn report claimed `allocate` was unsupported in a part *definition* body.
It is not:

[cols="2,1,1"]
|===
| Form | `part def` body | `part` usage body

| `allocate step to profile;`
| accepts
| accepts

| `allocate action step to profile;`
| *rejects*
| *rejects*
|===

The OMG corpus agrees: 22 `allocate` statements, none with a kind keyword on an
endpoint.

The two failing forms differ by a single token, and the reproduction had been built by
copying the model rather than by reducing to the smallest failing input.
Reducing would have dropped the `action` keyword and the bug would have evaporated —
which is why the checklist above now ends with a reduction step.

=== Model defect 6: chained `then` in a succession

A succession relates one source to one target.
`SuccessionAsUsage` takes a single `then`; chaining several in one statement is not
grammatical.

[source,sysml]
----
first start then receive then ship;    // invalid

first start then receive;             // valid — continue with the shorthand
then ship;
----

Across all 62 succession statements in the OMG corpus, *every one* has at most one
`then`: 16 are `first X;` with none, 46 have exactly one.
Upstream's own tests name the same model —
`action_body_accepts_first_without_a_then_clause`,
`action_body_still_accepts_first_then_succession`,
`then_succession_accepts_a_merge_node_target`.

*Not fixed.* Unlike defects 1–5 this one is widespread and mostly pre-existing:
14 files under `tools/sysmlv2/modeler/examples/workflow/` use the chained form, and
13 of them already failed `lint` under 0.49.0 for this and other reasons.
Only `workflow_14_grammar_probe.sysml` is in this spec's 18, and its name suggests
the chained form may be there deliberately to probe the grammar.
Cleaning up that directory is separate work, out of scope here — recorded so the row
in <<what-is-failing,What is failing, and why>> is not mistaken for an upstream gap.

== What to do about it

Raise upstream, do not work around.
Ranked by diagnostic count, the asks are: `ActionBodyItem` member coverage (23), a
nested `action def` (11), then the long tail.
Action bodies in aggregate are 38 of the 56, so that is where a fix pays best.
<<Upstream bug reports>> writes each one up.

The two highest-value asks are already filed as
https://github.com/elan8/sysml-v2-parser/issues/13[#13] and
https://github.com/elan8/sysml-v2-parser/issues/14[#14], along with
https://github.com/elan8/sysml-v2-parser/issues/16[#16] and
https://github.com/elan8/sysml-v2-parser/issues/17[#17] — 36 of the 56 diagnostics
between them.
Six reports remain unfiled; see <<Filing status>>.

Upstream is working the same ground from its own end: PR
https://github.com/elan8/sysml-v2-parser/pull/15[#15] documents *G31* — guarded
`succession a to b of <expr>;` not wired into action bodies — and *G32*, the nested
`action def` gap since fixed in 0.53.0.
G31 does not appear in this workspace's models, so it is not reported here; it is
worth knowing about because it is a third action-body gap, which strengthens the case
that `ActionBodyElement` needs a pass rather than piecemeal fixes.

At the time of that measurement `lint` failed on 18 files; see <<Status as of 0.53.0>>
for the re-measured counts.
Nothing in this workspace can close them — `lint` only chooses which entry point

As filed it lists six constructs, two of which this spec's
<<Evidence audit>> does not support:

`foreach`:: Not a SysML v2 keyword at all — the loop keyword is `for`, and `foreach`
  appears nowhere in the parser or in any OMG corpus.
  See <<Model defect 4: `foreach` is not SysML v2>>.
  Leaving this in invites the whole issue being closed as not-a-bug.
`snapshot`:: `snapshot` occurs 58 times in the OMG corpus but never inside an action
  body, so there is no precedent for this position.
  It may still be legal by the same `ActionBodyItem` argument as the others, but it
  is the weakest of the six.

The four well-evidenced constructs are `part`, `item`, `assert constraint` and
`variation` — and of those, `item` also lacks a direct corpus instance
(see <<Evidence audit>>).
Worth editing `#13` to drop `foreach`, and to mark `snapshot` and `item` as inferred
rather than attested.

[#bug-10]
=== Bug 10: `perform x.y redefines z;` keyword form

*Summary.* The `redefines` keyword is rejected where the `:>>` operator is
accepted.
The two are synonyms in the BNF.

*Reproduction.*

[source,sysml]
----
package Shop {
    action def Truing { action tighten; }
    part def Wheel { perform action truing : Truing; }
    part bike {
        part wheel : Wheel;
        perform wheel.truing redefines truing;
    }
}
----

----
unexpected token in part usage body
----

*Control.* `perform wheel.truing :>> truing;` is accepted.

[#bug-11]
=== Bug 11: `::>` feature chaining in `connect` endpoints

*Summary.* Endpoint feature chaining is rejected.

*Reproduction.*

[source,sysml]
----
package Shop {
    port def HubPort;
    part def Hub { port p : HubPort; }
    part def Rim { port p : HubPort; }
    part def Wheel {
        part hub : Hub;
        part rim : Rim;
        port hubPort : HubPort;
        port rimPort : HubPort;
        connect [1] hubPort ::> hub.p to [1] rimPort ::> rim.p;
    }
}
----

----
unexpected token in part definition body
----

*Control.* `connect [1] hub.p to [1] rim.p;` is accepted, so the multiplicity is
fine and `::>` is the gap.

[#bug-14]
=== Bug 14: assorted single-occurrence gaps

Each verified, each one diagnostic in this workspace.

Keyword-less binding in a package body::
+
[source,sysml]
----
package Shop {
    attribute def ScalarQuantity;
    attribute distance : ScalarQuantity;
    attribute volume   : ScalarQuantity;
    attribute scalarQuantities : ScalarQuantity[*];

    distancePerVolume :> scalarQuantities = distance / volume;
}
----
+
`unexpected keyword `distancePerVolume` in package body` — the diagnostic calls an
ordinary identifier a keyword.

`@Annotation about X { … }` in a package body::
+
[source,sysml]
----
package Shop {
    metadata def Rationale { attribute text : String; }
    part def Wheel;
    part wheel : Wheel;

    @Rationale about wheel {
        text = "chosen for stiffness";
    }
}
----
+
`incomplete parser support for annotation syntax in package body` — an unusually
candid diagnostic, and the only one here that names its own cause.

Qualified redefinition target in an occurrence body::
+
[source,sysml]
----
package Shop {
    part def Road { attribute incline : ScalarValues::Real; }
    part def Trip {
        occurrence road : Road;
        timeslice leg1 {
            snapshot start : Road {
                :>> Road::incline = 0;
            }
        }
    }
}
----
+
`unexpected token in occurrence body`.
*Control:* the unqualified `:>> incline = 0;` is accepted, so the gap is the
qualified name.

View usage body members::
+
[source,sysml]
----
package Shop {
    viewpoint def SafetyViewpoint;
    view def PartsTreeView;
    metadata def Safety;
    part def Wheel;
    package PartsTree { part wheel : Wheel; }

    view wheelTree : PartsTreeView {
        satisfy requirement sv : SafetyViewpoint;
        expose PartsTree::**;
        filter @Safety;
    }
}
----
+
`unexpected token in view body`.

=== Bug 15: diagnostics that describe the recovery position, not the mistake

*Status.* Filed with two sibling defects as
https://github.com/elan8/sysml-v2-parser/issues/18[issue #18], closed 2026-07-31.
Two of the three were fixed in 0.53.0, *exactly as this spec proposed*, and have been
removed from it:

[cols="1,2,2"]
|===
| Was | Proposed here | 0.53.0 emits

| 15b — an unrecognized identifier called a "keyword"
| ``unrecognized declaration `test` ``
| ``unrecognized declaration `test` in package body``

| 15c — a bare comma reporting the enclosing body
| `unexpected ',' … enclose a sequence in '( … )'`
| `unexpected ',' in feature value assignment; use sequence brackets '(a, b)' to
  assign multiple values` — and at the comma's own column
|===

15a — `expected unit name inside '[ ]'` reported where there is no `[` — is also gone
from this workspace, but was never minimized and is not demonstrably fixed: the string
still exists in `diagnostics.rs`, and what removed it here was the closing of the three
grammar gaps that triggered it, which this spec predicted might happen.
Removed as unreproducible rather than recorded as fixed.

*What survives.* The general defect: a diagnostic that names where recovery landed
rather than where the mistake is. Live on 0.53.0 —

[source,sysml]
----
package P {
    action c : Campaign {
        flow env to nullPoint.env;   // the offending token
        flow env to zeroPoint.env;
                                     // <- reported here, on a blank line
    }
}
----

The error for the mis-lexed `nullPoint` (see
<<literal-prefix,the literal-prefix bug>>) is
reported two lines further down, at a column on an *empty* line. That cost a full
bisection to locate, because the position pointed at whitespace.

No grammar change is implied. The fix is for recovery to carry the position of the
token that failed rather than the position at which scanning stopped.

*Where inference still carries weight.* The `ActionBodyItem` report rested partly on
inference — three of its six member kinds had no corpus instance in an action body —
and 0.53.0 fixing all of them settled it in inference's favour.
That is one data point, not a licence: the same shape of reasoning produced the five
withdrawals recorded above.
They are inside `#13` rather than filed separately, which is the right place for them:
a fix to `ActionBodyElement` covers all six, and a reviewer who rejects the weak three
can still act on the strong three.
Marking them as inferred when updating `#13` is worth doing.
