= Verdict-Parity Fallout
:toc: left
:toclevels: 3

`sysml-v2-parser` 0.50.0 stopped the strict parser silently accepting input it
could not parse.
That was the fix xref:02-parser-inconsistency.adoc[spec 02] asked for, and it
worked — but it also revealed every grammar gap the silence had been hiding.

18 project-authored `.sysml` files that passed `lint` under 0.49.0 now fail it.
This spec records which, why, and what is actually actionable, so the red gate is
a known quantity rather than a mystery.

Measured against `sysml-v2-parser` 0.50.0, comparing `lint --mode strict` verdicts
against a 0.49.0 build of the same crate.

== This is not a regression in this crate

Nothing in `sysml-v2-cli` changed behaviour.
The models did not change either.
What changed is that `parse_root` now reports what it previously dropped, so
constructs that were never being parsed are now visible as errors.

Upstream's own audit note (`PARSER_BACKLOG_ROADMAP.md` §6) states it plainly: the
grammar gaps were "previously masked by `parse_root` silently accepting them".
A clean `lint` run under 0.49.0 was therefore weaker evidence than it looked —
which is exactly what spec 02's second table predicted, now demonstrated at scale.

== The measurement

Across 259 project-authored `.sysml` files — excluding vendored OMG libraries,
`reference-examples/`, `standard-libraries/`, and build output:

| pass → pass
| 200

| pass → *fail* — the fallout
| 18

| fail → fail — already failing under 0.49.0

The 7 improvements come from 0.50.0's `loop`/`for`, requirement and

requirement examples, `13_banking_use_cases.sysml`, and
`campaign/00-meta-campaign/docs/explanation/sysml/action-flow-viewpoint.sysml`.

== What is failing, and why

56 substantive diagnostics across the 18 files, plus cascade-suppression notices.
55 of them trace to an upstream grammar gap.
The exception is the chained-succession row, which is a model defect left unfixed —
see <<Model defect 6: chained `then` in a succession>>.

Grouping by *diagnostic text* is misleading, because one message is emitted for
several unrelated constructs and several constructs produce more than one message

which is what a fix has to address.

Action bodies dominate: `part`, a nested `action def`, `part :>>`, `variation` and
`assert constraint` account for 38 of the 56.
`action_def_body_element` in upstream's `src/parser/action.rs` carries this comment
above its dispatch:

[quote]
____
SysML v2 ActionBodyItem includes both declarations and action behavior usages.
We support a pragmatic subset used by function-based behavior examples.
____

So these are acknowledged incompleteness, not rejected-because-invalid.
`PARSER_BACKLOG_ROADMAP.md` §6 lists G1–G30 as closed, but none of these
particular constructs appear there — they are gaps beyond that audit's scope.

=== A message that means nothing

`expected unit name inside '[ ]'` accounts for 10 of the 56 diagnostics and is
*not* tied to any one construct.
It appears for `part` in an action body, a nested `action def` and `part :>>` —
three unrelated constructs, and more before the withdrawn reports were removed.

In every observed case the reported line contains no `[` at all, and the reported
position is the header of an enclosing construct rather than anything resembling a
unit expression.
It is a mis-selected alternative's error surfacing as the file's verdict, not a
description of the input.
Written up separately in <<bug-15,Bug 15>>.

=== Do not "fix" the models — but do check the language first

Every construct in the table above is legal SysML v2, except the chained-succession
row, which is flagged there.
Rewriting a model to satisfy the parser would be the same mistake spec 02 records
having been made once already, when the recovery path's false positives "were read
as model defects for some time; they were not."

`sysml-v2-cli/tests/lint.rs::both_modes_reject_uncovered_grammar` pins five of these
gaps deliberately, so the release that closes them fails the suite and prompts this
spec to be revised.
Its companion, `accepts_the_valid_forms_of_constructs_we_once_misreported`, asserts
the correct spelling of all five withdrawn cases, so the corrected models cannot
regress and the withdrawals cannot quietly come back.

The converse trap is just as real, and this spec fell into it *five times* — every
time by treating "our model does this and the parser rejects it" as evidence the
parser was wrong.
Four are now fixed as model defects; the fifth is recorded but left alone:

[cols="2,3"]
|===
| Written | Should have been

| `test case def X { … }`
| `verification def X { … }` — there is no `test` keyword

| `part :>> readings = a, b;`
| `= (a, b);` — `=` takes one expression

| `foreach x in xs { … }`
| `for x in xs { … }` — there is no `foreach` keyword

| `allocate action step to profile;`
| `allocate step to profile;` — endpoints are feature references, not declarations

| `first a then b then c;`
| one `then` per statement, continued with `then c;`
|===

Between them these accounted for 28 of the 83 substantive diagnostics originally
recorded here — 27 removed by the fixes, and one (the chained succession) still
present.
Two were caught in review rather than by measurement, and three more by the audit
those reviews prompted — because *measurement confirms what the parser does, never
whether it is right to do it*.

So before filing a gap, establish that the construct is real, independently of this
workspace's models.
<<Evidence audit>> applies the following to every surviving report:

* Check whether the parser has the token at all.
  `grep -r '"test"' src/parser/` and `grep -rn foreach src/` both returned nothing —
  which settles those two on their own.
* Look for the construct, *in the same body kind*, in OMG-authored SysML v2: the
  domain and systems libraries under `tools/sysmlv2/discussion/stds/sysmlv2/`, the
  `SimpleVehicleModel` from the OMG PTC 2025 submission at
  `tools/sysmlv2/discussion/docs/example/ptc-25-04-31.sysml`, and the training and
  pilot examples under `tools/sysmlv2/modeler/reference-examples/`.
  Position matters: `allocate` appears 22 times in that corpus, but never once in a
  part *definition* body, and never with a kind keyword on its endpoints.
* Find a *control* the parser accepts that expresses the same intent.
  If one exists, suspect the model.
  `allocate step to profile;` is accepted in the very body where
  `allocate action step to profile;` is not.
* *Reduce to the smallest input that still fails*, rather than trimming the model
  around the construct.
  The `allocate` report survived because its reproduction was copied from a model and
  kept a stray `action` keyword; dropping one token at a time would have found that
  immediately.

A diagnostic that names a construct is not evidence the construct is real.

== The real defects found

Six genuine model defects surfaced.
All are fixed.
Together they took the fallout from 29 files to 18, and they are the concrete
argument for adopting 0.50.0 despite the red gate: the honest parser found real
bugs that four prior releases had hidden.

=== Model defect 1: `:` where `:>` was meant

`granule/surrogate/decepticon-surrogate/sysmlv2/transport.sysml` declared four
part definitions with a typing operator instead of a specialization operator:

[source,sysml]
----
part def CameraChannel : ZmqChannel {      // was
part def CameraChannel :> ZmqChannel {     // now
----

`:` is a `FeatureTyping` and is only legal on a *usage*; a `part def` specializes
with `:>`.
The previous form had no valid reading, so nothing was lost in correcting it —
and 0.50.0's diagnostic named the fix outright:

----
invalid typing operator in part definition specialization: use ':>' instead of ':'
----

All four occurrences were corrected and the file now lints clean in both modes.

=== Model defect 2: `test case def` is not SysML v2

Six `test_cases.sysml` files — `carla-system/{flyer,npc,perception,validator}` and
`surrogate/{perceptacum,simulacrum}-surrogate` — opened their case definitions with
a construct the language does not have:

[source,sysml]
----
test case def WheelIsRound {           // was — no `test` keyword exists
verification def WheelIsRound {        // now
----

The SysML v2 form is `verification def`, per `VerificationCaseDefinition` in the
BNF.
Upstream implements it as `verification_case_def` in `src/parser/case.rs`, keyed on
the `verification` keyword with `def` required.

Verified: the parser accepts `verification def`, `case def` and `use case def`, and
has no `test` token anywhere.
All six files now lint clean in both modes; `test case def` was the sole cause of
failure in every one of them.

This one was initially misfiled as an upstream gap, on the strength of the
diagnostic's wording alone:

----
unexpected keyword `test` in package body
----

Calling `test` a "keyword" made it look like a recognized-but-unimplemented
construct.
It is not: the parser has no `test` token at all, and this is its generic report for
an unrecognized leading identifier — the same wording it produces for
`distancePerVolume` in <<bug-14,Bug 14>>.
The phrasing is worth fixing upstream in its own right; filed as <<bug-15,Bug 15>>b.

=== Model defect 3: bare comma list where a sequence constructor was meant

`campaign/surrogate/benchmark-surrogate/sysml/benchmark-surrogate-campaign.sysml`
and `campaign/teds-playground/sysml/carla-system-campaign.sysml` each bound a
plural feature with a bare comma list:

[source,sysml]
----
part :>> parameters = loadLevel, messageRate;      // was
part :>> parameters = (loadLevel, messageRate);    // now
----

The base declaration is `part parameters : Parameter[1..*];`, so a collection is
wanted — but `=` takes a single expression, and a sequence needs `( … )`.

This one is unambiguous: two lines below the defect, the *same file* already used
the correct idiom for a different feature —

[source,sysml]
----
attribute :>> values = (10, 50, 100);
----

— so the parenthesized form was known to the author and simply missed here.
The OMG standard libraries use the same form throughout.

Both occurrences corrected.
Each file still fails on a genuine `foreach` gap, so the failing-file count is
unchanged; the diagnostic count drops by two.

The bracket form `= [pressure, tension];` is also rejected.
That is very likely correct — `[ ]` is multiplicity in SysML v2, not a sequence
literal — but it was not checked against the BNF, so it is an observation only, not a
claim.

The diagnostic this produced was itself misleading, and is filed as
<<bug-15,Bug 15>>c.

[CAUTION]
====
Case bodies are not validated.
`verification def V { attribut x : String; }` — with a misspelled keyword inside —
is accepted, because upstream captures the body with `loose_use_case_body`.
The same holds for `case def` and `use case def`.
So these six files now *parse*, but their bodies are not being checked, and the
`subject` / `verify` / `attribute` members inside them are effectively unverified.
This is the same class of gap as
xref:02-parser-inconsistency.adoc#_upstream_bug_report[issue #12] and is worth
adding to it.
====

=== Model defect 4: `foreach` is not SysML v2

The loop keyword is `for`.
`foreach` does not exist — `grep -rn foreach src/` over the parser returns nothing,
and it appears nowhere in any OMG corpus, while `for` appears in both the standard
libraries and the training examples.

[source,sysml]
----
foreach cfg in configurations { … }        // was
for cfg in configurations { … }            // now
----

19 occurrences across five files:
`campaign/00-meta-campaign/sysml/{example-campaign/campaign,meta/parameter-space}.sysml`,
`campaign/surrogate/benchmark-surrogate/sysml/benchmark-surrogate-campaign.sysml`,
`campaign/teds-playground/sysml/carla-system-campaign.sysml`, and
`tools/sysmlv2/discussion/docs/example/camp/camp-inst.sysml`.
All corrected; 8 diagnostics removed.

Upstream implements this as `for_loop` in `src/parser/action.rs`, wired into both
`ActionDefBodyElement` and `ActionUsageBodyElement`.
Verified: `for s in spokes { … }` and `for n in (1, 2, 3) { … }` are both accepted.

=== Model defect 5: a kind keyword on an `allocate` endpoint

`allocate`'s endpoints are `ConnectorEndMember` — references to features that already
exist — not declarations.
Our models prefixed the source with `action`:

[source,sysml]
----
allocate action step to profile;      // was
allocate step to profile;             // now
----

`step` is already declared as `action step : TruthStep;` earlier in the same body, so
the keyword was both redundant and ungrammatical.

34 occurrences across five files:
`campaign/00-meta-campaign/sysml/meta/{experiment-pkg,experiment-workflow}.sysml`,
`campaign/surrogate/benchmark-surrogate/sysml/benchmark-surrogate-experiment.sysml`,
`campaign/teds-playground/sysml/carla-system-experiment.sysml`, and
`tools/sysmlv2/discussion/docs/example/exp/exp-exec.sysml`.
All corrected; 11 diagnostics removed.

*This was the clearest false gap of the five*, because the body kind was a red
herring.
The withdrawn report claimed `allocate` was unsupported in a part *definition* body.
It is not:

[cols="2,1,1"]
|===
| Form | `part def` body | `part` usage body

| `allocate step to profile;`
| accepts
| accepts

| `allocate action step to profile;`
| *rejects*
| *rejects*
|===

The OMG corpus agrees: 22 `allocate` statements, none with a kind keyword on an
endpoint.

The two failing forms differ by a single token, and the reproduction had been built by
copying the model rather than by reducing to the smallest failing input.
Reducing would have dropped the `action` keyword and the bug would have evaporated —
which is why the checklist above now ends with a reduction step.

=== Model defect 6: chained `then` in a succession

A succession relates one source to one target.
`SuccessionAsUsage` takes a single `then`; chaining several in one statement is not
grammatical.

[source,sysml]
----
first start then receive then ship;    // invalid

first start then receive;             // valid — continue with the shorthand
then ship;
----

Across all 62 succession statements in the OMG corpus, *every one* has at most one
`then`: 16 are `first X;` with none, 46 have exactly one.
Upstream's own tests name the same model —
`action_body_accepts_first_without_a_then_clause`,
`action_body_still_accepts_first_then_succession`,
`then_succession_accepts_a_merge_node_target`.

*Not fixed.* Unlike defects 1–5 this one is widespread and mostly pre-existing:
14 files under `tools/sysmlv2/modeler/examples/workflow/` use the chained form, and
13 of them already failed `lint` under 0.49.0 for this and other reasons.
Only `workflow_14_grammar_probe.sysml` is in this spec's 18, and its name suggests
the chained form may be there deliberately to probe the grammar.
Cleaning up that directory is separate work, out of scope here — recorded so the row
in <<What is failing, and why>> is not mistaken for an upstream gap.

== What to do about it

Raise upstream, do not work around.
Ranked by diagnostic count, the asks are: `ActionBodyItem` member coverage (23), a
nested `action def` (11), then the long tail.
Action bodies in aggregate are 38 of the 56, so that is where a fix pays best.
<<Upstream bug reports>> writes each one up.

The two highest-value asks are already filed as
https://github.com/elan8/sysml-v2-parser/issues/13[#13] and
https://github.com/elan8/sysml-v2-parser/issues/14[#14], along with
https://github.com/elan8/sysml-v2-parser/issues/16[#16] and
https://github.com/elan8/sysml-v2-parser/issues/17[#17] — 36 of the 56 diagnostics
between them.
Six reports remain unfiled; see <<Filing status>>.

Upstream is working the same ground from its own end: PR
https://github.com/elan8/sysml-v2-parser/pull/15[#15] documents *G31* — guarded
`succession a to b of <expr>;` not wired into action bodies — and *G32*, which is
<<bug-2,Bug 2>>.
G31 does not appear in this workspace's models, so it is not reported here; it is
worth knowing about because it is a third action-body gap, which strengthens the case
that `ActionBodyElement` needs a pass rather than piecemeal fixes.

Until those land, `lint` fails on 18 files.
Nothing in this workspace can close them — `lint` only chooses which entry point
to call — and the alternative, pinning back to 0.49.0, buys a green gate by
restoring a parser that silently accepted typos.
That trade was considered and declined.

=== Bug 1: `ActionBodyItem` coverage — structural members in action bodies

*Filed as https://github.com/elan8/sysml-v2-parser/issues/13[issue #13]* (open).

CAUTION: `#13` as filed also lists `foreach` and `snapshot`.
`foreach` is not a SysML v2 keyword and should be removed from the issue — see
<<Filing status>>.
Three of the members below rest on inference rather than corpus precedent: `item`,
`snapshot` and the `part :>>` anonymous-redefinition form.
`part`, `assert constraint` and `variation` are attested in action bodies and carry the
argument; the other three are worth marking as inferred when updating the issue.

*Summary.* An action body accepts only a subset of `ActionBodyItem`.
Structural members that the spec admits are rejected.
27 of the 56 diagnostics in this workspace come from this one gap — 38 counting the
nested `action def` of <<bug-2,Bug 2>> — making it by far the highest-value fix.
`action_def_body_element` already documents itself as "a pragmatic subset".

*Reproductions.* Each fails independently.

[source,sysml]
----
package Shop {
    part def Wheel;
    action def Truing {
        part rim : Wheel;                       // unexpected keyword `part` in action body
    }
}
----

[source,sysml]
----
package Shop {
    item def Spoke;
    action def Truing {
        item spokes : Spoke[*];                 // unexpected keyword `item` in action body
    }
}
----

NOTE: `for s in spokes { … }` in the same position *is* accepted, as is
`for n in (1, 2, 3) { … }`.
An earlier draft of this report also listed `foreach`, which is not a SysML v2
keyword at all — see
<<Model defect 4: `foreach` is not SysML v2>>.
A separate, genuine loop gap is <<bug-16,Bug 16>>.

[source,sysml]
----
package Shop {
    action def Truing {
        assert constraint { 1 > 0 }             // unexpected keyword `assert` in action body
    }
}
----

[source,sysml]
----
package Shop {
    action def Truing {
        variation action method {                // unexpected keyword `variation` in action body
            action byHand;
            action byJig;
        }
    }
}
----

[source,sysml]
----
package Shop {
    action def Truing {
        snapshot trued { }                      // unexpected keyword `snapshot` in action body
    }
}
----

[source,sysml]
----
package Shop {
    action def Assembly {
        part :>> station { }                    // unexpected keyword `part` in action body
    }
}
----

*Control.* `action tighten;`, `for s in xs { … }` and a plain `first a then b;` in the
same position are all accepted, so the dispatch itself works — it is the member kinds
that are missing.

The anonymous-redefinition form above has its own control: the identical member inside
a *part usage* body is accepted, which is what makes the action-body rejection look
like a coverage gap rather than a grammar rule.

[source,sysml]
----
package Shop {
    part def Tube;
    part def Frame { part seatTube : Tube; }
    part bike : Frame {
        part :>> seatTube { }                   // accepted
    }
}
----

*OMG precedent, in an action body specifically.*
`part` — `Parts.sysml:51` in the Systems Library
(`ref part this : Part :>> Action::this, …`) and
`3e-Function-based Behavior-item.sysml:28`.
`assert constraint` — six occurrences, including `Dynamics.sysml:40` and
`Vehicle Analysis Demo.sysml:140`.
`variation` — `VehicleVariabilityModel.sysml:127`
(`variation action generateTorque : GenerateTorque {`).
`item`, `snapshot` and the `part :>>` form have no direct precedent in the corpus in
this position.
They are included because they reach `ActionBodyItem` through the same
`DefinitionElement` production as `part`, which is attested — and, for `part :>>`,
because the identical member is accepted in a part usage body.
That is inference rather than evidence, weaker than the three above, and worth saying so
in the issue.
`snapshot` is the weakest: it occurs 58 times in the corpus, never once in an action
body.

=== Bug 2: `action def` nested inside a part definition body

*Filed as https://github.com/elan8/sysml-v2-parser/issues/14[issue #14]* (open).

NOTE: Independently corroborated upstream.
`PARSER_BACKLOG_ROADMAP.md` gained this as *G32* in PR
https://github.com/elan8/sysml-v2-parser/pull/15[#15], found while adapting Spec42 to
0.50.0 and described there as "`PartDefBodyElement` has no `ActionDef` variant at all
… unlike its already-supported siblings `StateDef`/`MetadataDef`/`FlowDef`/
`RequirementDef`".
That is the same asymmetry argument as below, reached from a different direction — the
strongest confirmation any report here has.

*Summary.* `action def` is the *only* definition kind rejected inside a `part def`
body.
Seven others are accepted in the same position, so this is an isolated omission
rather than a general restriction on nesting.
Accounts for 11 diagnostics, and is the sole cause of failure in four files here.

*The asymmetry.* Same body, same `{ }`, only the keyword changes:

[cols="2,1"]
|===
| Nested in `part def Outer { … }` | Verdict

| `attribute def A { }`
| accepts

| `item def I { }`
| accepts

| `port def P { }`
| accepts

| `part def P2 { }`
| accepts

| `calc def C { }`
| accepts

| `state def S { }`
| accepts

| `constraint def K { }`
| accepts

| `action def A2 { }`
| *rejects*
|===

*OMG precedent.* Nested definitions inside a `part def` body occur 16 times in the
corpus — for example `attribute def CartInput :> Input {` in `CartSample.sysml:8` and
`attribute def VehicleInput :> Input {` in `EVSample.sysml:11`.
No `action def` instance appears, so the precedent is for the *category* rather than
this keyword; the seven-of-eight asymmetry above is the stronger argument.

*Reproduction.*

[source,sysml]
----
package Shop {
    part def TileCache {
        action def GetTile { }
    }
}
----

----
expected ';' or '{' after action definition header
----

The diagnostic is also misleading: a body *is* present.

*Control.* Both of these are accepted, isolating the gap to the nested `def` form:

[source,sysml]
----
package Shop {
    part def TileCache {
        action getTile;             // usage — accepted
    }
}
----

[source,sysml]
----
package Shop {
    action def GetTile { }          // same definition at package level — accepted
}
----

=== Bug 5: `interface` usage as a body member

*Filed as https://github.com/elan8/sysml-v2-parser/issues/16[issue #16]* (open).

*Summary.* An `interface` *usage* is rejected as a member of a part definition
body, with or without a `connect` clause.
`interface def` at package level is accepted, as is a plain `connect`.

*Reproduction.*

[source,sysml]
----
package Shop {
    port def HubPort;
    interface def SpokeInterface { end p1 : HubPort; end p2 : HubPort; }
    part def Hub { port p : HubPort; }
    part def Rim { port p : HubPort; }

        part rim : Rim;

----

unexpected token in part definition body
----

*The `connect` form additionally misreports.*
Written across two lines — the layout the OMG spec Annex examples use — the
diagnostic becomes a semicolon complaint about a construct that needs no
semicolon there:

[source,sysml]
----
        interface hubToRim : SpokeInterface
            connect [1] hub.p to [1] rim.p;
----

----
missing semicolon before next declaration
----

*Control.* `connect hub.p to rim.p;` and `connect [1] hub.p to [1] rim.p;` are both
accepted in the same position, so neither `connect` nor endpoint multiplicity is
the problem — it is the `interface` usage member.

=== Bug 15: diagnostics that describe the recovery position, not the mistake

Three related diagnostic-quality defects, no grammar change implied.
Worth filing together, and worth filing *first*: two of them actively caused
mis-diagnosis during this investigation, and they make every gap above harder to
read.

==== 15a. `expected unit name inside '[ ]'` where there is no `[`

*Summary.* Reported for inputs containing no `[` on the reported line, at a position
belonging to an unrelated enclosing construct.
It accounts for 10 of the 56 diagnostics here, across three unrelated constructs:
`part` in an action body, a nested `action def` and `part :>>`.

*Observed behaviour.* The same declaration produces different messages depending on
unrelated content elsewhere in the file.

The clearest case: two files each contain, inside an `action def` body, the
character-for-character equivalent member — same feature name, same type — and it
is the <<bug-1,Bug 1>> gap in both:

[source,sysml]
----
        part deployment : K8sDeploymentContext;
----

----
a.sysml:263:9: unexpected keyword `part` in action body
b.sysml:39:9:  expected unit name inside '[ ]'
----

Neither line contains a `[`, and in `b` there is no `[` anywhere near it.

In one traced instance the trigger was a `[0, 255]` *inside a doc comment*, 247
lines below the reported position: bracketed text in a comment within the recovery
region appears to be scanned as a unit expression, and the resulting error is then
selected as the file's verdict.

*Not yet minimized.*
Short reproductions have so far resisted — an unsupported construct plus a comment
containing `[0, 255]`, in isolation, reports the ordinary message.
The trigger needs more surrounding structure than that.
Filing this with the honest description above is more useful than a synthetic
example that does not reproduce it — and closing the grammar gaps in
the grammar gaps above may well remove the opaque-capture regions that produce it, in
which case this resolves on its own.

[NOTE]
====
The first evidence for this bug came from two `test case def` files, which turned
out to be an invalid construct (<<Model defect 2: `test case def` is not SysML v2>>)
and are now fixed.
The phenomenon is unaffected: 21 occurrences remain, spread over six constructs
that *are* valid SysML v2, and the two-file contrast above is drawn from those.
====

*Suggested direction.* Two things are worth separating: whether the alternative
that produces the message should be reachable at all in these positions, and
whether comment content can leak into token scanning during recovery — the latter
being the same class of defect as
xref:01-fix-comment-block.adoc[spec 01], which was fixed for the bare-feature
heuristic but perhaps not for bracket scanning.

==== 15b. An unrecognized identifier is called a "keyword"

*Summary.* When a body element begins with an identifier the parser does not
recognize, the diagnostic names it as a keyword:

----
unexpected keyword `test` in package body
unexpected keyword `distancePerVolume` in package body
----

Neither `test` nor `distancePerVolume` is a keyword — the first is not in the
language at all, the second is an ordinary feature name.

*Why it matters.* This wording inverts the reader's diagnosis.
"Unexpected keyword X" reads as *"X is a construct I know but do not support here"*,
which points at the parser.
The truth is *"X is not anything I recognize"*, which points at the input.
It cost this investigation a full mis-filed report: `test case def` was recorded as
an upstream gap on the strength of this phrasing alone, before anyone checked whether
SysML v2 has a `test` keyword.
It does not — see <<Model defect 2: `test case def` is not SysML v2>>.

*Suggested wording.* `unrecognized declaration `test`` — or, when the token is
genuinely a keyword in the wrong place, keep the current phrasing and reserve it for
that case.

==== 15c. A bare comma reports the enclosing body, not the comma

*Summary.* `part :>> readings = a, b;` — a comma-separated list where a sequence
constructor is required — reports:

----
unexpected token in part definition body
----

The parser closes the feature-value expression at the comma and then tries to read
`b` as the next body element, so the position it reports is the body rather than the
comma.

*Why it matters.* The message gives no hint that `( … )` is what is missing, and
names a location the author did not write anything wrong at.
This also produced a mis-filed report — see
<<Model defect 3: bare comma list where a sequence constructor was meant>>.

*Suggested wording.* `unexpected ',' in feature value — enclose a sequence in
'( … )'`, which turns a confusing recovery failure into a self-answering message.
