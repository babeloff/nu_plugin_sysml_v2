= Fix Comment Block
:toc: left
:toclevels: 3

[NOTE]
====
*Resolved in `sysml-v2-parser` 0.50.0.*
This spec is retired and kept for provenance.
The behaviour it asked for is now guarded by
`sysml-v2-cli/tests/lint.rs::comment_prose_is_not_read_as_a_declaration`.
====

It should be possible to use `/** ... */` comment blocks.

Through 0.49.0 one shape of comment was mis-parsed: the error-recovery parser
stopped treating a comment as a comment partway through it and read the rest of
the comment body as code.

== The defect

A multi-line comment inside a *part definition body* was truncated by the
error-recovery parser when one of its continuation lines looked like a typed
feature declaration — that is, when the line read `<identifier>: <text>`.
The parser reported the comment's own prose as an invalid declaration:

----
bare feature `Optional : some text */` is not valid in a part definition body
----

The quoted text is the comment's second line, and — when the colon line was the
last line of the comment — it included the closing `*/`.
That was the tell: the lexer had resumed scanning inside the comment body and no
longer knew it was in a comment.

Reproduction, `probe.sysml`:

[source,sysml]
----
package P {
    part def C {
        /** first line
            Optional: a profile may state the rate */
        attribute x : String;
    }
}
----

Under 0.49.0 this passed `lint --mode strict` and failed `lint --mode edit`.
Moving the colon to the comment's first line made it pass in both.

Only the error-recovery path (`parse_for_editor` → `parse_with_diagnostics`) was
affected; the strict `parse` entry point always accepted it.
Because `lint` defaults to strict, the defect could never fail a normal `lint`
run — the impact was on editor and LSP tooling built on the recovery path, and on
model authors having to avoid a natural English construction ("Optional: …",
"Note: …") on any line but the first.

It applied to `/** … */`, `/* … */` and `doc /* … */` alike, and only inside a
part-definition body — `package`, `action def`, `attribute def`, `port def` and
`part` usage bodies were all unaffected.
A colon on the comment's first line never triggered it, and neither did
`Word = text`, `Word; text`, `Word text`, a two-word phrase before the colon, or a
qualified name such as `see ISQ::TimeValue for details`.

== Resolution

Fixed upstream, as this spec's original "where a fix belongs" section predicted —
nothing in this crate could address it, since `lint` only chooses which entry
point to call.

Two commits on
https://github.com/elan8/sysml-v2-parser[`elan8/sysml-v2-parser`],
both referencing https://github.com/elan8/sysml-v2-parser/issues/1[issue #1] —
now closed — and merged as PR
https://github.com/elan8/sysml-v2-parser/pull/4[#4] from
`fix/comment-block-recovery-issue-1`, first released in 0.50.0:

`ee9b8a9`:: "Fix multi-line block comment false bare-feature warnings" — tracks
  `/* */` across newlines in the part-def heuristic, so comment prose is no longer
  read as a declaration.
`f64335d`:: "Remove non-spec bare-feature-in-part-def diagnostic" — drops the
  `bare feature … is not valid in a part definition body` check altogether,
  because SysML §7.6.4 permits a `DefaultReferenceUsage` with no kind keyword.
  The diagnostic was therefore wrong in its own right, not merely mis-firing
  inside comments.

Verified against 0.50.0: all three comment forms, every trigger condition listed
above, and continuation lines in both middle and final position — 54 cases — are
accepted by *both* `strict` and `edit`.
The five previously-unaffected contexts stay clean.

One consequence of `f64335d`: `edit` no longer reports a keyword-less feature such
as `someBareFeature : String;` in a part-definition body at all.
Per the §7.6.4 citation that construct is legal, so this is a false positive
removed rather than a check lost.

=== Follow-through completed

. The `ComputeProfile.targetRunTime` doc comment in
  `campaign/00-meta-campaign/sysml/meta/compute-environment.sysml` has been
  reverted from `Optional, since …` to `Optional: …`, and lints clean in both
  modes.
  That rewording had existed only to avoid this defect.
. The regression test asserts both modes accept the reproduction, for all three
  comment forms.
. The corresponding note has been removed from
  xref:../how-to/lint-sysml-files.adoc[the lint how-to].

The broader strict-versus-recovery divergence this was one instance of is
xref:02-parser-inconsistency.adoc[spec 02]; the constructs that 0.50.0's fix for
*that* divergence turned into hard errors are
xref:03-verdict-parity-fallout.adoc[spec 03].
