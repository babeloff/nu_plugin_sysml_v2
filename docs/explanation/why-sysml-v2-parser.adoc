= Why `sysml-v2-parser`, not `syster`

The granule toolchain (`granule/00-meta-granule/shared-scripts/syster-*.nu`)
previously validated `resources.sysml` files with `syster`
(`syster-base`/`syster-cli`), an independently authored SysML v2/KerML
parser and semantic analyzer. The switch to `sysml-v2-parser` was made
because `syster` seemed less mature overall — not a single precisely
diagnosed root cause. Two concrete things observed along the way:

* `undefined reference: 'StorageCapacityValue'` even with
  `private import ISQ::*;` in scope.
* A parse error on `out item state : T;`, treating `state` as a keyword in
  that grammar position rather than an ordinary identifier —
  `tests/lint.rs::rejects_state_as_a_plain_identifier_case` checks that
  `sysml-v2-parser` accepts it.

`sysml-v2-parser` is syntax-only: it never attempts import or stdlib
resolution, so it structurally can't produce the first kind of issue —
though that also means it can't catch type errors or undefined references
at all, semantic or otherwise. Its `DiagnosticCategory::UnresolvedSymbol`
exists only for *callers* to classify their own semantic findings — the
parser itself never emits it.

This mirrors a migration already done elsewhere in the granule toolchain
(`channel-adapter`'s `sysml-emit` crate, commit `9c68329c`, "switched to
sysml-v2-parser") — `sysml-v2-cli`'s `emit` subcommand is in fact that same
crate's AST-walking/lowering machinery, moved here because it's generic
SysML v2 processing rather than specific to any one granule package. See
xref:architecture.adoc[the architecture explanation] for how that lowering
pipeline works.

== `--resolve-imports` adds resolution back, deliberately scoped

`--resolve-imports`/`--lib-dir`
(see xref:../how-to/resolve-imports-against-a-library.adoc[the how-to guide])
does add import/reference resolution — the category of check `syster` also did.
Two things distinguish it from just re-adding that risk:

* *Off by default.* Plain `lint`/`emit` never changes behavior;
  you have to explicitly ask for the stricter check,
  so nobody gets a surprise false positive from a check they didn't know was running.
* *An explicit, inspectable index, not a built-in stdlib model.*
  `--lib-dir` resolves against whatever `.sysml` files you actually point
  it at — if `ISQ::StorageCapacityValue` doesn't resolve, the fix is
  visible and local: your `--lib-dir` doesn't have the file that defines
  it, not an opaque, un-auditable model baked into the tool.
