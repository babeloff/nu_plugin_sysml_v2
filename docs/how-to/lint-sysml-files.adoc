= How to lint SysML v2 files

== Lint one or more files

[source,bash]
----
sysml-v2-cli lint resources.sysml
sysml-v2-cli lint a.sysml b.sysml c.sysml
----

Exit code `0` means every file parsed with no syntax errors; `1` means at
least one didn't. Both the summary and any error text go to stdout either
way — nothing goes to stderr.

== Get structured output instead

[source,bash]
----
sysml-v2-cli lint --json resources.sysml
----

Emits a JSON array, one object per input file, each with `file`, `ok`, and
an `errors` array (see xref:../reference/cli.adoc[the CLI reference] for the
exact shape). Useful for feeding into `jq` or another script.

== Lint from Nushell instead of the CLI

If you're already in a Nushell pipeline (e.g. iterating over
`glob **/*.sysml`), use the plugin instead of shelling out:

[source,nu]
----
open --raw resources.sysml | lint sysml
----

Returns a record `{ok, errors}` rather than text — see
xref:use-the-nushell-plugin.adoc[using the Nushell plugin].

== Choose how much detail you get

`sysml-v2-parser` has two entry points, and `lint` lets you pick:

[source,bash]
----
sysml-v2-cli lint --mode strict resources.sysml   # the default
sysml-v2-cli lint --mode edit   resources.sysml
----

Since `sysml-v2-parser` 0.50.0 the two agree on the *verdict* for every file, so
this is a choice about diagnostic verbosity rather than about which answer to
believe:

`strict` (default)::
  Stops at the first error. The right choice for a CI gate.

`edit`::
  The error-recovery path, the one an editor or LSP sees. Reports every problem in
  the file rather than the first, which is what you want when fixing a model.

Before 0.50.0 the two disagreed in both directions, and `strict` would silently
drop a declaration it could not parse — so a missing semicolon or a misspelled
keyword could pass `lint` entirely.
If you are comparing against an older run, that is why counts changed.

== Expect failures on known parser gaps

Current as of `sysml-v2-parser` 0.53.0.
142 of 568 project models fail `lint` on constructs that are legal SysML v2 but that
the parser does not yet cover.

0.53.0 closed most of the gaps this section used to list.
Verified by direct probe as now *accepted*:

* `part p : A;` in an action-definition body
* `action def X { … }` nested in a part-definition body
* `interface x : T;` as a part-definition body member
* `exhibit state X parallel { … }`
* `part :>> name { … }` in a part usage body
* `assert constraint { … }` and `variation` in an action body
* `allocate … to …;` in a part-definition body

Still open:

* a typed loop variable — `for n : ScalarValues::Integer in (1, 2, 3)` — where the
  untyped form is accepted
* *new in 0.52.0:* a bare feature value assignment in a usage body, as in
  `part x : T { packageName = "x"; }`.
  0.52.0 made connection/interface body diagnostics visible for the first time and
  this is what they revealed.
  It is legal — 56 occurrences in the OMG official pilot examples — and it is the
  form every granule's `resources.sysml` uses, so thirteen of them went red on the
  bump.

*Do not rewrite a model to satisfy these.* They are upstream gaps; nothing in this
crate can close them, since `lint` only chooses which entry point to call.
xref:../specs/03-verdict-parity-fallout.adoc[Spec 03] lists every affected file,
the diagnostic counts, the minimal reproductions to raise upstream, and the
re-measurement against 0.53.0.

Two things `lint` catches that *are* worth acting on, because they are genuinely not
SysML v2: `part def X : Y` — a `part def` specializes with `:>`, and the diagnostic
names the fix — and `%%% garbage %%%`-style unparseable content in a body, which
both modes reject as of 0.53.0 and neither caught before it.

`sysml-v2-cli/tests/lint.rs` pins the current behaviour of each gap, so the release
that closes them fails the suite and prompts these notes to be retired rather than
letting them go quietly out of date.
